## 三、Windows 门禁：24 红 → 0 红

基线在 Windows 上实跑：**800 passed / 24 failed / 13 skipped**。逐项定位后分为五类，
全部是平台差异，没有生产逻辑错误，但其中两类会造成真实的数据损坏：

| 根因 | 用例数 | 修法 |
|---|---|---|
| 文本 IO 未指定 encoding（Windows 默认 cp936） | 17 | 106 处 `read_text/write_text/open` 补 `encoding="utf-8"`；26 处 `subprocess(text=True)` 补 `encoding="utf-8", errors="replace"` |
| `.gitattributes` 只钉 `*.js`，workflow YAML 检出为 CRLF | 5 | 补 `*.yml/*.yaml text eol=lf`；测试抠脚本前统一 `\r\n → \n` |
| `bash` 被 CreateProcess 解析到 System32 的 WSL 垫片 | 5（与上条重叠） | 测试改用 Git Bash 绝对路径；找不到就 skip，而不是假红 |
| `submit.js` 硬编码 `python3` | 1 | 依次尝试 `$PYTHON` → `python3` → `python`；子进程 stdin/stdout 显式 UTF-8 |
| DJYY 预算 0 的边界依赖 `monotonic` 精度 | 1 | 判定从 `>` 改 `>=`：零预算 = 立即截止 |

修复后同一环境：**845 passed / 13 skipped / 0 failed**（无任何环境变量）。

为什么必须修：本机是 Windows，`scripts/njstats_duty.py` 就在这里写
`data/state/*.json` 并 commit 到仓库，再由 Linux CI 读取。写侧落 GBK、读侧按 UTF-8
解析会直接崩；`engine/learning/elo_updater.py` 的 `_load()` 在读中文队名时也会炸。
这不是测试洁癖，是跨机器数据完整性问题。

新增 `tests/test_io_encoding.py` 做静态守卫：再有人漏写 `encoding=`，
PR 阶段就红，不用等某台机器偶发。
